# Rule / Skill 编写纪律（四条原则 + 一条前置判断）

> 风格借鉴 [andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills)：简洁、通用、直接、可自检。
>
> **使命**：产出 AI 能稳定执行、任何系统/平台/语言都能套用、每条断言都能被 diff 或行为验证的 rule / skill。

**权衡说明**：本纪律偏向精简优先。一次性个人偏好走对话即可，不必每次都走完整流程。

---

## 0. 先判断：Rule 还是 Skill？

**不要两个一起写。选一个最合适的载体。**

| 诉求 | 载体 |
|---|---|
| 持续约束 AI 行为（风格、禁止项、命名） | Rule |
| 打包完整工作流 / 操作步骤 / 方法论 | Skill |
| 针对特定文件类型生效（`**/*.ts`、`**/*.vue`） | Rule + `globs` |
| 用户显式"启动"的复杂任务（创建 PR、配置环境） | Skill |
| 每次对话都要注入的底线要求 | Rule + `alwaysApply: true` |

**自检**：它是"AI 干活时的约束"还是"AI 要完成的任务"？约束 → Rule；任务 → Skill；两者都是 → 拆成两个文件。

---

## 1. 明确用途 + 分工定位

**先写下具体问题，再找已有 rule 的边界。不要为不存在的问题建规则，也不要和已有规则职责重叠。**

- **写下一句话具体问题**（谁、在什么时候、怎么错了），不能具体化 → 目标太虚，停手。
- **先搜已有 rule / skill**，有覆盖就合并或扩展，**不要新建**。
- 与已有规则相关但不重叠时，在开头 blockquote 写清**分工定位 + 冲突优先级**（例："与 X-guidelines 分工：X 管 HOW，本规则管 WHAT；冲突时本规则优先"）。

反模式：
- ❌ "先写一个代码审查规范，以防万一" → 不是具体问题。
- ❌ 没搜已有规则就新建，导致职责重叠。
- ✅ "AI 生成的 commit 经常漏 `Made-with: Cursor` trailer，必须强制" → 具体、可验证。

**自检**：这条规则能在一次 diff / 一次对话 / 一个 PR 里，看到具体的行为差别吗？看不到 → 目标太虚，回头重写问题陈述。

---

## 2. 极简优先 + 不造术语

**一文件一主题。短断言代替长解释。用人人都懂的词，不发明概念。**

- 一条 rule 只讲一件事。两件 → 拆成两个文件。
- 优先**短断言 bullet**（例："不要为一次性代码写框架"）。**不要**为了凑结构硬塞表格 / 反例三件套。
- **禁止**铺陈背景、哲学、愿景、心得感悟。
- **禁止自造术语**（例：`基线` / `档位` / `升档` / `XX 矩阵` / `N 维分析`）。确需新概念，首次出现用一句话定义，或直接换成人话表达。
- **禁止**同一断言用"表格 + bullet + 反模式"三种形式讲三遍。一种够了。

**自检**：把内容删掉一半，规则还能执行吗？能 → 那一半是废话，删掉。

---

## 3. 通用性 + 具体指令

**写任何系统 / 任何语言 / 任何平台都能套用的断言。不绑定领域术语，也不给模糊建议。**

- **禁止领域绑定**：不出现 `N+1` / `QPS` / `pytest` / `Redux` 这类仅对特定技术栈有意义的词，除非整条规则就是针对该技术栈。
- **禁止模糊动词**："尽量"、"考虑"、"建议"、"最好" → 全部改成"必须"、"禁止"或可执行动作。
- 可以使用**编程通用词**：`抽象`、`配置`、`循环`、`缓存`、`调用`、`异常` —— karpathy 也用。
- 反例 / 正例（❌/✅）**可选**，断言本身够清楚就不需要画蛇添足；karpathy 多数条目并无示例。
- 举例时，例子要具体到能想象出来（例："200 行能写成 50 行时重写"），不要抽象到"代码要精简"。

**自检**：把这条断言搬到另一种语言 / 另一个平台，还成立吗？不成立 → 说明绑定了领域，改成更抽象的表述。

---

## 4. 每条原则可自检

**每个 `##` 原则节结尾必须有一句 `**自检**：[反问]？[触发] → [动作]`。文件末尾必须有整体生效信号。**

- **每条原则级自检**：让 AI 读到该节后能立即自己回答 yes/no 并知道怎么补救。
- **自检句结构**：**反问句**（能否做到 X？）→ **触发答案**（不能 / 没有）→ **动作**（补上 / 回头问 / 删除 / 重写）。
- **文件末尾整体信号**：bullet 列表或 ≤ 5 条 checklist，描述"规则生效时能在 diff / 对话 / 代码里看到什么"。
- Skill 额外要求：多步流程**每一步**要有"验证点"，整体要有明确的"完成标准"。

**自检**：数一下本文件有几个 `##` 原则节，再数一下有几个 `**自检**：` 出现，相等吗？不相等 → 补上缺的那条。

## Frontmatter 速查

```yaml
---
description: 一句话说清"做什么 + 何时触发"，让 AI 能自动判断激活
globs: **/*.ts        # 可选，按文件激活
alwaysApply: false    # true 会每次对话都加载，慎用
---
```

激活优先级：`alwaysApply: true` > `globs` 匹配 > `description` 触发词匹配。

## 落地检查清单

- [ ] 目标问题具体、可复现，不是"以防万一"
- [ ] 载体选对（Rule vs Skill）
- [ ] 与已有相关规则的**分工 / 冲突优先级**写明在开头 blockquote
- [ ] **无自造术语**；确需新词已在首次出现时一句话定义
- [ ] **无领域绑定**（除非整条规则就是针对该领域）
- [ ] 每条原则结尾都有 `**自检**：...` 句
- [ ] 文件末尾有整体"生效信号"或 checklist
- [ ] 把内容删掉一半仍然可执行（简洁性检验）

---

## 这些原则生效的信号

- rule / skill 文件**短小干净**，无冗余、无自造词、无领域绑定。
- AI 读完能**直接执行**，不需要二次澄清。
- **换一种语言 / 平台 / 技术栈**，规则依然适用（除非是针对该栈的规则）。
- diff / 对话 / PR 里能**肉眼看出**规则的效果。
- 团队成员 **30 秒**能理解规则作用与适用范围。
