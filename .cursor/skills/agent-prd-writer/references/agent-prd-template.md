## 1. 文档概述 Overview

### 1.1 一句话产品定义

> 用一句话说清楚：**给谁（用户）× 在什么场景 × 通过什么方式 × 帮他完成什么事 × 带来什么价值**
>
> 示例："为保险公司理赔员提供一个嵌入工单系统的 AI Copilot，在 30 秒内自动审阅事故证据并生成理赔建议，将平均处理时长从 25 分钟降到 8 分钟。"

### 1.2 核心价值主张

- 对用户：（节省时间 / 提升质量 / 降低门槛 / 24h 在线 / ...）
- 对业务：（降低成本 / 扩大规模 / 提升 NPS / 解锁新场景 / ...）

### 1.3 关键成功指标（North Star）

| 指标类型 | 指标名称 | 基线 | 目标 | 度量方式 |
|---|---|---|---|---|
| 业务指标 | 任务处理时长 | 25 min | ≤ 10 min | 工单系统打点 |
| 产品指标 | 周活 DAU / MAU | - | ≥ 40% | 埋点 |
| 体验指标 | 用户满意度 CSAT | - | ≥ 4.2/5 | 会话末尾问卷 |
| 质量指标 | 任务完成率 | - | ≥ 85% | 评测 + 线上抽检 |

## 3. 目标用户与场景 Users & Scenarios

### 3.1 用户画像（Persona）

至少写 1-2 个主要 Persona，每个包含：
- 角色 / 职位
- 日常工作任务与使用频次
- 现在遇到的痛点
- 对 AI 的认知水平与态度（会不会用 / 会不会怀疑）
- 典型设备环境（PC Web / 移动 / 嵌入在其他系统）

### 3.2 核心场景故事（User Story）

用"**作为……，我希望……，以便……**"句式写出 3-7 个主场景。每个故事后面附一个**具体的对话 / 交互示例**，这比抽象描述重要 10 倍。

示例：
> **作为**一名新入职的客服，
> **我希望**在遇到不熟悉的工单时，能快速拿到同类历史工单的处理方案，
> **以便**我能在第一次回复中就给出准确答案，不被客户投诉新人不专业。
>
> **示例对话：**
> 客服：有个用户说他的订单支付成功但显示待付款
> Agent：这类「支付成功状态未同步」问题，过去 30 天有 142 单，主因分 3 类：
> 1. 风控拦截（占 58%）→ 引导用户 24h 内重新登录
> 2. 支付回调延迟（32%）→ 手动触发对账
> 3. 用户重复点击（10%）→ 订单去重
> 建议先确认用户订单号，我帮你查一下属于哪类。

## 4. 产品定位与 Agent 形态 Positioning

### 4.1 Agent 形态（选择 + 理由）

| 形态 | 是否采用 | 理由 |
|---|---|---|
| 对话式 Chatbot（独立入口） | ☐ | |
| 嵌入式 Copilot（侧边栏 / inline） | ☐ | |
| 后台自主执行 Agent（无 UI） | ☐ | |
| 定时任务型 Agent（cron） | ☐ | |
| Multi-Agent 协同 | ☐ | |
| 语音 / 多模态 Agent | ☐ | |

### 4.2 自主性等级（Autonomy Level）

参考自动驾驶分级法，明确你的 Agent 处于什么级别：

| Level | 描述 | 人机分工 |
|---|---|---|
| L1 · 建议器 | 只给建议，人全权决策 | 人 100% |
| L2 · 辅助执行 | 人发起后代劳 | 人决策，Agent 执行 |
| L3 · 条件自主 | 特定场景全自主 | Agent 主，人兜底 |
| L4 · 高度自主 | 大多数场景自主 | 人监督，异常介入 |
| L5 · 完全自主 | 不需要人 | - |

> 明确写出：**本项目目标为 L___，MVP 先做到 L___**

### 4.3 产品原则（Product Principles）

3-5 条在遇到产品决策两难时拍板用的原则。例如：
- **Accurate over Fluent**：宁可少说也不要说错
- **Transparent**：始终说明信息来源，用户可追溯
- **Reversible**：所有自主执行的动作都可撤销

### 6.X 任务 X：[任务名称] · 优先级 P?

#### 6.X.1 任务描述

- **用户意图**：用户在什么情境下会发起这个任务？具体说什么话、点什么按钮？
- **期望结果**：用户拿到什么才算满足？（一段文本？一个文件？一次动作的执行回执？）
- **典型触发示例**（列 3-5 条真实用户可能说的话）：
  1. "……"
  2. "……"
  3. "……"

#### 6.X.2 交互流程（Happy Path）

用**带注释的示例对话 / 时序图**呈现理想路径。避免只用文字描述。

​```
用户：[输入]
  └─ Agent 理解：识别意图 = X，槽位 = {a: ?, b: ?}
  └─ 槽位 a 缺失 → 澄清提问
用户：[补充 a]
  └─ Agent 调用工具：search_order(a)
  └─ 工具返回：[...]
  └─ Agent 组织回复：
Agent：[输出]
  └─ 提供操作按钮：[确认] [取消] [查看详情]
​```

#### 6.X.3 输入规范

- **文本输入**：最长 N 字 / 支持语种
- **文件输入**：支持格式、大小上限、数量上限
- **结构化输入**（如果嵌入其他系统）：字段列表

#### 6.X.4 输出规范

- **格式**：纯文本 / Markdown / JSON / 富文本卡片 / 文件
- **长度**：建议上限、分段策略
- **必含元素**：结论、依据、下一步建议、引用来源、置信度标识
- **禁止元素**：外链、代码块（如不需要）、情绪化表达、过度寒暄

#### 6.X.5 依赖能力 & 工具调用

| 能力 / 工具 | 类型 | 用途 | 失败兜底 |
|---|---|---|---|
| 知识库检索 | RAG | 提供事实依据 | 返回"我没有查到相关信息" |
| 工单系统 API | Tool Call | 查订单状态 | 超时 3s 后返回友好错误 |
| LLM 推理 | Core | 生成回复 | 模型 fallback 到备用 |

#### 6.X.6 验收标准

- [ ] 在评测集 X 上任务完成率 ≥ N%
- [ ] 首 token 延迟 P90 ≤ N ms
- [ ] 输出符合《输出规范》10 条中至少 9 条
- [ ] 在 M 个对抗性 prompt 上无安全红线违规

## 7. Agent 架构设计 Agent Architecture

> 这一章不是给 PM 看的，是给研发看的。所以要**清晰但不过度**——架构细节放 TDD，PRD 只写产品视角的能力组合。

### 7.1 高层架构图（文字或 Mermaid）

​```mermaid
graph LR
    U[用户] --> UI[前端]
    UI --> Router[意图路由]
    Router --> Agent1[主 Agent]
    Agent1 --> RAG[知识库]
    Agent1 --> Tools[业务工具]
    Agent1 --> Memory[会话记忆]
    Agent1 --> Safety[安全护栏]
    Agent1 --> UI
​```

### 7.2 能力组件清单

| 组件 | 职责 | 所有者 | 依赖 |
|---|---|---|---|
| 意图识别 | 把用户输入分类到 N 种任务 | 算法 | LLM |
| 知识库（RAG） | 提供事实依据 | 算法 + 运营 | 向量库 / ES |
| 工具 / 插件 | 对接业务系统 | 后端 | 业务 API |
| 会话记忆 | 多轮状态保持 | 后端 | 数据库 |
| 安全护栏 | 输入输出过滤 | 算法 + 法务 | 规则库 |
| 监控与埋点 | 追踪效果与异常 | 数据 | 埋点平台 |

### 7.3 工具 / 插件清单（Tool Catalog）

每个被 Agent 调用的工具都要列清楚：

| Tool Name | Description（给模型看的） | 入参 | 出参 | 幂等? | 是否需审批 |
|---|---|---|---|---|---|
| `search_order` | 根据订单号查订单状态 | order_id | {status, amount, user_id} | ✅ | 否 |
| `refund` | 发起退款 | order_id, amount | {refund_id, status} | ❌ | 是 |
| `escalate_to_human` | 转接人工 | reason | {ticket_id} | ✅ | 否 |

### 7.4 记忆与上下文管理

- 短期记忆：本轮会话保留多少 turn
- 长期记忆：是否记住用户偏好、如何写入 / 更新 / 读取
- 跨会话隔离：不同用户 / 不同会话如何避免串号

## 8. 模型行为契约 Model Behavior Contract

> 这一章定义 Agent 的"人设 + 语气 + 格式 + 拒绝风格"。不是技术 prompt，而是产品对模型行为的期望描述，给评测、给标注、给后续模型迭代都要用到。

### 8.1 人设（Persona）

- 名字 / 称谓（是否需要给 Agent 起名？）
- 语气：专业 / 亲切 / 简洁 / 幽默？
- 身份自述边界：可以说"我是 AI 助手"还是假装人？（默认强烈建议表明 AI 身份）

### 8.2 输出风格

- 是否使用第一人称 "我"
- 是否使用表情符号 / emoji
- 是否使用加粗、列表、表格
- 长回复的组织方式（先结论后解释 / 先背景后建议）
- 语言：仅中文 / 仅英文 / 自适应

### 8.3 拒绝与澄清风格

| 场景 | 推荐话术 | 反模式 |
|---|---|---|
| 超出能力范围 | "这超出了我的能力，但我可以帮你 X / 联系 Y" | "我不会" / "抱歉，我是 AI 助手不能……" |
| 信息不足 | 明确问缺失的 1-2 个关键字段 | 一次问 5 个问题 / 用户还没说完就追问 |
| 可能答错 | "根据 X，我的理解是 Y，但建议你再确认 Z" | 假装很确定 / 频繁"可能" "也许"稀释回答 |

### 8.4 Few-shot 对比示例（推荐放 ≥ 5 组）

​```
Input: [用户输入]
Good Output:
  [期望的输出]
  ↑ 为什么好：简洁、有依据、给出下一步
Bad Output:
  [要避免的输出]
  ↑ 为什么不好：冗长、推诿、越权
​```

## 9. 评测方案 Evaluation

> 没有评测的 Agent PRD 是半成品。这一章必须让算法和 QA 能直接排期开干。

### 9.1 评测维度矩阵

| 维度 | 子指标 | 度量方式 | 上线门槛 | 持续监控? |
|---|---|---|---|---|
| 任务完成率 | End-to-end success rate | 评测集 + 人工标注 | ≥ 85% | ✅ |
| 事实准确率 | Factuality | 对照知识库核对 | ≥ 95% | ✅ |
| 幻觉率 | Hallucination rate | 人工标注 | ≤ 3% | ✅ |
| 拒答合理性 | Refusal appropriateness | 双人标注 | ≥ 90% | 抽样 |
| 安全合规 | Red-teaming pass rate | 对抗测试集 | 100% | ✅ |
| 体验质量 | CSAT / Thumbs-up | 用户反馈 | ≥ 4.2/5 | ✅ |
| 延迟 | TTFT / P95 端到端 | 埋点 | ≤ 2s / ≤ 8s | ✅ |
| 成本 | ¥/task | 账单 | ≤ ¥0.15 | ✅ |

### 9.2 评测集建设

- **静态测试集**：规模、来源、标注规范、版本管理
- **动态对抗集**：红队定期更新、越狱测试用例
- **线上抽样**：比例 N%、脱敏、人工复审流程
- **A/B 基线**：对比对象（旧版 / 人工基线 / 竞品）

### 9.3 上线门控

| 阶段 | 要求 |
|---|---|
| Dev 冒烟 | 核心任务 ≥ 70% 完成 |
| 内测 α | 指标达 80%，无 P0 安全问题 |
| 灰度 β（5% → 20% → 50%） | 指标稳定，CSAT ≥ 4.0 |
| 全量 GA | 全部门槛达成 + 法务合规签字 |

## 10. 失败、幻觉与兜底 Failure & Fallback

### 10.1 失败模式清单

| 失败类型 | 典型表现 | 检测方式 | 兜底策略 |
|---|---|---|---|
| 模型拒答 | "我无法回答" | 正则 + 分类模型 | 转人工 / 重试不同 prompt |
| 模型幻觉 | 编造不存在的事实 | 与 RAG 结果对照 | 加引用强制 / 降级为建议性回答 |
| 工具超时 | API 无响应 | 3s timeout | 降级回答 + 后台重试 |
| 工具返回异常 | 非预期格式 | Schema 校验 | 进入错误处理分支 |
| 越权请求 | 用户要求做 OOS 操作 | 意图分类 | 拒绝 + 解释 |
| 对抗注入 | Prompt Injection | 输入扫描 | 忽略注入 + 记录 |

### 10.2 Human-in-the-Loop 介入点

明确在哪些节点必须有人类参与：
- 金额 ≥ X 的退款建议 → 必须客服经理确认后执行
- 置信度 < 0.6 的回答 → 标注"AI 初稿，请审核"
- 连续 3 轮用户不满意 → 主动提出转人工

### 10.3 用户教育与期望管理

- 首次使用引导：告诉用户 AI 能做什么、不能做什么、怎么反馈
- 每次 AI 生成内容旁：展示 "AI 生成" 标识 + 反馈按钮（👍 / 👎 / 报错）
- 免责声明：放在什么位置、什么文案

### 11.3 规模化优化路径

- **蒸馏**：高频场景用小模型蒸馏 → 中长期

## 12. 合规、安全与数据 Compliance

### 12.1 数据处理

| 数据类型 | 来源 | 是否涉及 PII | 存储位置 | 保留期 | 脱敏策略 |

| 对话历史 | 生成 | 是 | 业务库 | 180 天 | 账号级隔离 |
| 知识库 | 运营整理 | 否 | 向量库 | 长期 | - |

### 12.2 模型与第三方服务
