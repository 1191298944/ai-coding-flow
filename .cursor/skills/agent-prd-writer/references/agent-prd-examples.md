# Agent PRD 示例片段

> 本文件提供 2 个真实领域的示例片段（非完整 PRD），供参考**语气、详尽度、关键元素如何落地**。
> 写实际 PRD 时，应以 `agent-prd-template.md` 为骨架，参考下面这些片段的颗粒度。

## 示例一：客服工单 Copilot

### 1.1 一句话产品定义（示例）

> 为 XX 电商平台客服团队提供一个嵌入工单系统的 AI Copilot，在客服回复用户前自动给出建议话术、相关历史工单、操作入口（退款 / 改地址），让一线客服人均日处理工单数从 55 提升到 80，首次响应准确率提升 30%。

### 6.1 核心任务：工单初诊与话术建议（P0）

#### 6.1.1 任务描述

- **用户意图**：客服打开一个新工单，希望快速了解用户问题、定位类型、拿到可参考的回复草稿。
- **期望结果**：Copilot 在 3 秒内呈现：①问题分类 ②相似历史工单 TOP 3 ③建议回复草稿 ④可一键执行的操作按钮。
- **典型触发**：
  1. 客服点开新工单（自动触发）
  2. 客服在 Copilot 面板点"重新分析"
  3. 客服问 Copilot："这种情况一般怎么处理？"

#### 6.1.2 交互流程（Happy Path）

​```
[工单打开事件] → Copilot 自动拉取工单上下文
    ├─ 调用 classify_issue(ticket) → 类型 = "支付失败-风控拦截"
    ├─ 并行调用 search_similar_tickets(ticket) → 返回 3 条历史工单
    ├─ 并行调用 check_user_risk(user_id) → 返回风控状态
    └─ 组装 prompt → LLM 生成回复草稿

Copilot 面板展示：
  【问题类型】支付失败 · 风控拦截（置信度 92%）
  【相似工单】
    1. #T-8821 · 3 天前 · 同类问题已解决 [查看]
    2. #T-8432 · 1 周前 · 同类问题已解决 [查看]
    3. ...
  【建议话术】（点击复制 / 直接发送）
    "您好，经查询，您的订单因风控规则暂时拦截。请您在 24 小时内..."
  【操作入口】[发起风控复核] [引导用户重登] [转高级客服]
​```

#### 6.1.3 输出规范（摘录）

- 话术长度：80-180 字，不超过 3 段
- 必含元素：
  - 礼貌开头（您好 / 感谢等待）
  - 基于用户订单号的具体信息（不说"您的订单"，要说"您尾号 1234 的订单"）
  - 清晰的下一步指引（用户该做什么）
  - 预期时效（多久能解决）
- 禁止元素：
  - 无依据的承诺（"保证 24 小时内解决"）
  - 推卸责任（"这是系统的问题"）
  - 过度道歉（连续 3 个"非常抱歉"）

#### 6.1.4 模型行为契约（示例对比）

​```
Input: 用户工单：订单 #O-20240512-1234 显示已支付但状态未更新，客户情绪激动。

Good Output:
  【问题类型】支付状态不同步（置信度 88%）
  【建议话术】
    "您好，非常理解您的焦急。经核查，您尾号 1234 的订单已完成支付，
    但因支付回调延迟导致状态未同步。我已为您手动触发对账，预计 10 分钟内
    恢复正常，届时系统会自动发货。如超过 30 分钟仍未更新，请回复本工单，
    我会立即升级处理。"
  【操作入口】[手动触发对账] [升级到支付专员]

  ↑ 为什么好：
    - 确认了具体订单号
    - 给了明确时效（10/30 分钟）
    - 有兜底动作（升级）
    - 不说"我们会尽快"这种虚指

Bad Output:
  "非常抱歉给您带来不便！我们会尽快为您处理，请您耐心等待。"
  ↑ 为什么不好：
    - 完全没有定位问题
    - 无时效承诺
    - 没有实际动作
    - 像一个没用的机器人
​```

## 示例二：研发代码 Review Agent（Multi-turn + Tool use）

### 6.1 核心任务：PR 自动审阅（P0）

#### 6.1.1 任务描述

- **用户意图**：研发提交 PR 后，希望在人工 review 之前拿到一份结构化的自动审阅报告，覆盖：代码风格、潜在 bug、测试覆盖、文档完整性。
- **期望结果**：一个评论区 Bot 在 2 分钟内发布审阅报告；对每条问题打分（必修 / 建议 / 可选）并附修改建议。

#### 6.1.2 能力边界（关键片段）

- **In-scope**：
  - 代码静态问题（命名、复杂度、重复）
  - 明显的 null/空值/边界遗漏
  - 测试覆盖缺失检查
  - 与团队规约一致性（从 `coding-guide.md` 读取）
- **Out-of-scope**：
  - 架构层面重构建议（留给人类）
  - 业务逻辑正确性（无法判断）
  - 性能调优（除非有明显模式）
- **Edge Cases**：
  - 超大 PR（> 1000 行变更）：只审阅"高风险文件"，其他出摘要
  - 生成代码（autogen / protobuf）：跳过不审
  - 第三方库升级型 PR：只审 Changelog 相关点

#### 6.1.3 工具清单（片段）

| Tool | Description | 入参 | 出参 | 审批 |
|---|---|---|---|---|
| `get_pr_diff` | 拉取 PR diff | pr_id | diff 文本 | 否 |
| `run_linter` | 跑静态分析 | file_paths[] | issues[] | 否 |
| `search_repo` | 在仓库搜类似模式 | query | matches[] | 否 |
| `read_guide` | 读取团队规约 | section | text | 否 |
| `post_comment` | 发评论到 PR | body | comment_id | ❗ 需审核 |

> 说明：`post_comment` 需要审核 = 先存草稿，由用户（该 PR 作者或 owner）一键确认后才发布到 PR。避免 Agent "自说自话" 发满评论区。

#### 6.1.4 失败 & 兜底（片段）

| 失败 | 兜底 |
|---|---|
| LLM 误报"bug"但实际不是 | 用户可标记"误报"，该规则在该仓库下权重降低 |
| PR 过大超过上下文 | 拆分审阅：按文件/按模块分批，最后汇总 |
| Linter 挂了 | 降级为仅 LLM 审阅 + 在评论中声明"静态扫描缺失" |
| 模型输出格式异常 | JSON schema 校验 → 重试 1 次 → 降级为纯文本 |

## 使用本文件的方法

1. 写 PRD 前先通读一遍，感受**细节该写到什么颗粒度**
2. 对应章节写不出来时，回来找这里类似的片段**迁移结构**
3. 不要照搬文案，要**按用户场景重写**，否则会出现很多不贴的细节
