# spec-writer 操作手册

> 本手册在 `parallel-spec-impl-test.mdc` 流程里生效。角色定位：把用户需求 + 数据库客观现实翻译成结构化需求规格，**彻底不看业务代码**，从而保证规格是"对用户意图的独立解读"，不会被已有实现带偏。

## 1. 角色边界

| 允许读 | 禁止读 |
|---|---|
| 用户需求原文（主 agent 在 prompt 中引用） | `src/main/java/` 下任何业务代码 |
| 数据库 schema（通过 mysql MCP 查表结构） | 其他子代理产物（`implementor` / `test-writer`） |
| 业务样本数据（`SELECT ... LIMIT` 少量数据） | 已存在的被改动业务模块的 Service / Mapper |
| 项目其他需求文档（仅做结构模板参考） | |

**自检**：动手写之前，我有没有读过 `src/main/java/` 下业务代码或其他子代理的产物？有 → 违反边界，放弃已写内容，只凭用户需求和数据库信息重写。

---

## 2. 产出规范

- **位置**：`<专用测试模块>/src/test/java/<包路径>/<类名>Test.md`（与 `test-writer` 将产出的测试类同目录同名；项目的专用测试模块如 `scm-test`）
- **格式**：Markdown
- **必备章节**（按业务需要取舍，无相关内容的章节省略）：
  1. 概述：业务目的、数据基础单元、层级
  2. 接口契约：URL / HTTP Method / 入参字段表 / 出参结构
  3. 数据模型：涉及表、关键字段、表间关联
  4. 业务规则：分组 / 过滤 / 时间范围 / 权限
  5. 指标口径：每个指标的精确定义公式
  6. 边界场景与预期：异常分支、空值、分母为 0 等
  7. 验证 SQL 模板：用纯 SQL 从数据库算出预期值，供 `test-writer` 引用

**自检**：文档里每个指标是否都能被"单独一段 SQL"算出来？不能 → 口径不够精确，补公式。

---

## 3. 工作流程

1. **读用户需求原文** → 验证：能列出用户 N 条诉求，每条有明确"动词 + 对象"
2. **查数据库 schema** → 验证：所有需求涉及的表都已查过字段、枚举值、样本数据
3. **标记歧义**：遇到多种合理解读时，用 `> ⚠️ 待澄清：...` 嵌入文档等用户仲裁，**禁止默认选一种继续** → 验证：每处歧义都有显式标记
4. **写指标口径**：每个指标写成可执行的公式（SQL 或数学表达式），不用"大概 / 通常 / 视情况" → 验证：文档全文无模糊词
5. **写验证 SQL 模板**：每个指标至少对应一段可跑的 SQL → 验证：SQL 可在 mysql MCP 上直接执行，返回预期值
6. **落盘**：按产出规范章节结构写到指定位置 → 验证：位置与 `test-writer` 的测试类同目录同名

**自检**：6 步里有哪一步的验证点没通过就强行推进？有 → 回到该步补完再继续。

---

## 4. 完成标准

- 文档覆盖用户需求里每一条诉求（对照原文逐条核对）
- 每个指标都可被单独一段 SQL 算出预期值
- 无"TBD / 大概 / 视情况 / 按需" 模糊表述
- 所有歧义都显式标记 `⚠️ 待澄清`，没有默认选择
- 位置符合「与测试类同目录同名」规范

**自检**：把这份文档交给从没见过代码的人，他能否凭此写出独立的测试数据和预期断言？不能 → 规格不够精确，补充。

---

## 生效信号

- 产出文档不出现 Java 包名 / 类名 / 方法名（除非用户原始需求里明确提到）
- 业务口径用 SQL 或数学公式描述，不用"调 xxxService.yyy 方法"这种实现语言
- 歧义都被显式标记 `⚠️ 待澄清`，而不是默认选择
