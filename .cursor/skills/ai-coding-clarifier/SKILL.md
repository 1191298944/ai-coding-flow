# ai-coding-clarifier

文件读写权限与存储路径 → 见 **ai-coding-file-conventions skill**。
通用约束（文件合规/歧义处理/返回格式）→ 见 **ai-coding-sub-agent rule**。

## 使用场景

用户需求口语化、存在歧义、边界不清时，通过一次结构化表单将需求固化为 `context.md`，增量记录变更历史，支持跨 Chat、跨账号的需求延续。

**禁止**：读任何业务代码——读了会被既有实现带偏。

**自检**：有没有打开或读取任何 `src/` 下的文件？有 → 立即停止，只看用户原始输入。

---

## 输入

- 用户原始需求原文
- 业务名（修订时传入；首次不传，自行提议）

**自检**：追加模式下是否有业务名？没有 → 向调用方请求，不自行假设或新建。

---

## 执行流程

1. **分析歧义**：读用户原文，识别所有不明确点（字段范围、排序规则、分页、权限、异常处理等）；修订时必读已有 `context.md` 的「当前需求」节作为本轮起点。

2. **一次性结构化提问**：将所有歧义点合并为**单次 AskQuestion 表单**，每个问题给候选答案，不让用户自由回答。
   → **验证**：只发一次 AskQuestion，不分轮次批次。

3. **处理异议**：用户选完后，若某答案仍不清晰（用户说"都不对"或补充新信息）→ 只针对该点追加单次追问，其余已确认问题不再重复。
   → **验证**：追问只涉及有异议的点，不重新发全量表单。

4. **确认归档**：展示需求摘要（3~5 条，≤ 50 字/条）+ 建议业务名，`AskQuestion` 让用户选「确认归档 / 继续澄清」。
   - 继续澄清 → 回到步骤 3，只针对仍有争议的点
   - 确认归档 → 进入步骤 5
   → **验证**：用户明确选了"确认归档"，clarifier 不自行判定"差不多了"。

5. **写 context.md**：
   - 首次：新建文件，写入全部节
   - 修订：覆盖写「当前需求」和「接口契约」节；在「变更历史」末尾追加一行
   → **验证**：「变更历史」只追加，不删除历史行；「当前需求」是最新状态，不保留旧版内容。

---

## 输出

输出：业务名（调用方据此派生路径，无需 clarifier 回传绝对路径）

**自检**：返回值里有没有绝对路径或文件内容？有 → 删除，只报业务名。

---

## context.md 内容结构

```
# <业务名>

## 当前需求
<贴近用户原文的需求陈述，覆盖写入>

## 接口契约
<URL / Method / 核心入参字段 / 核心出参字段>
（澄清阶段用户未提及接口细节时省略此节）

## 变更历史
- [YYYY-MM-DD V1] 初始：<一句话描述>
- [YYYY-MM-DD V2] 修改：<变更摘要>
```

**约束**：
- 「当前需求」贴近用户原文，不含对话往返、AI 说明
- 「接口契约」只含契约信息（URL / Method / 入出参），不含业务规则或 SQL
- 「变更历史」每次归档追加一行，历史行不删除

**自检**：「当前需求」里有没有 `user：` / `ai：` / `问：` / `答：` 这类对话格式？有 → 删除，只保留需求陈述原文。

---

## 完成标准

- `context.md` 写入 `~/.cursor/.llm/<业务名>/` 目录
- 「当前需求」只含需求陈述，无对话往返、无 AI 分析
- 「变更历史」追加了本轮变更行（历史行数只增不减）
- 业务名为合法路径片段（全小写 + 连字符，无中文 / 空格）
- 输出时只报业务名

---

## 生效信号

- 首轮只发一次 AskQuestion，不分批次
- 追问只针对有异议的点，不重复已确认问题
- `context.md` 的「当前需求」是一段纯需求陈述，看不到任何 `user：` / `ai：` 字样
- 「变更历史」行数随归档次数单调递增，不会减少
- 输出只有业务名字符串
